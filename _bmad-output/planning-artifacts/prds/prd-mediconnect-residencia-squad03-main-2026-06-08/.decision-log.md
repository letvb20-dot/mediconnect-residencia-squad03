# Log de Decisões: PRD MediConnect

Este log registra todas as decisões de design, sobreposições e alinhamentos-chave feitos durante o desenvolvimento do Documento de Requisitos de Produto (PRD).

---

## Entradas do Log

### [2026-06-08] Inicialização do PRD
- **Decisão:** Sessão de elaboração de novo PRD iniciada para a plataforma de gestão clínica MediConnect.
- **Justificativa:** O usuário (Lanse) solicitou ajuda com planejamento e documentação do projeto e optou pelo Fast Path.
- **Status:** Aprovado

### [2026-06-08] Idioma do Documento
- **Decisão:** PRD traduzido para **Português Brasileiro** a pedido do usuário. `communication_language` e `document_output_language` devem ser atualizados no `_bmad/bmm/config.yaml` para `Portuguese` e `Portuguese` respectivamente.
- **Status:** Aprovado — atualizar config se necessário.

### [2026-06-08] Calibração de Stakes
- **Decisão:** PRD calibrado como **Ferramenta Interna / Equipe → aproximando-se de Lançamento**. Este é um projeto de residência (RiseUP Squad 03) com backend Supabase real e deploy em produção (Vercel). Rigor definido correspondentemente: cobertura completa de RF com consequências testáveis, métricas de sucesso e não-objetivos.
- **Status:** Aprovado

### [2026-06-08] Modo de Trabalho
- **Decisão:** Fast Path escolhido pelo usuário. PRD completo elaborado com tags `[PREMISSA]`. Usuário irá revisar e iterar.
- **Status:** Aprovado

### [2026-06-08] Persistência da Fila de Espera — Confirmada como localStorage
- **Decisão:** Investigação do código confirmou que `waitlistRepository.js` usa exclusivamente `localStorage` (chave `mediconnect.waitlist.v1`). Documentado como pós-MVP na §6.2. Pergunta em aberto #1.
- **Justificativa:** Nenhuma tabela Supabase para fila de espera identificada no codebase. Risco de bloquear lançamento do MVP.
- **Status:** Documentado — aguarda decisão de produto sobre quando migrar.

### [2026-06-08] Fila de Consultas — Confirmada como localStorage
- **Decisão:** `visitRepository.js` usa exclusivamente `localStorage` (chave `mediconnect.consultationQueue.v1`). Documentado como pós-MVP.
- **Status:** Documentado.

### [2026-06-08] WhatsApp — Implementado via Edge Function (NÃO simulado)
- **Decisão:** `communicationRepository.js` linha 69 confirma chamada real para `functionsUrl/send-whatsapp`. WhatsApp está implementado com tratamento de resposta e log. NÃO é simulado. SMS usa Twilio. E-mail apenas aparece como canal nos logs/filtros, sem função de envio.
- **Justificativa:** Código real contradiz a premissa inicial de "todos os canais além de SMS são simulados". PRD atualizado para refletir esta distinção.
- **Status:** Aprovado — Pergunta em aberto #2 permanece sobre credenciais de provedor WhatsApp.

### [2026-06-08] Tabela de Prontuários — Padrão de Fallback (sem tabela canônica)
- **Decisão:** `medicalRecordRepository.js` linha 4 define `MEDICAL_RECORD_TABLES = ['medical_records', 'patient_records', 'records']` e tenta as três em sequência. Nenhuma tabela é canônica no código — depende do schema Supabase existente. PRD documenta o padrão de fallback como comportamento atual e mantém Pergunta em aberto #3 para definição do schema.
- **Status:** Documentado — requer alinhamento com schema Supabase real da equipe.

### [2026-06-08] Segurança da Chave de API de IA — Sinalizado mas sem bloqueio
- **Decisão:** O padrão atual de chave Claude no cliente é aceitável para o escopo de demonstração/residência. Um `[NOTA PARA PM]` está embutido no RF-14 marcando como bloqueador pré-produção.
- **Status:** Reconhecido.

### [2026-06-08] Rota de Prontuários — Correção Incluída no MVP
- **Decisão:** Conectar `MedicalRecordsPage` a `/prontuario/:id` está incluído no escopo do MVP (RF-15). O código + RBAC existente está completo; apenas o registro de rota em `App.jsx` está faltando.
- **Justificativa:** Baixo esforço, alto impacto. Deixar desconectado seria uma lacuna de qualidade para o lançamento.
- **Status:** Aprovado.

### [2026-06-08] E-mail como Canal
- **Decisão:** E-mail é reconhecido nos logs e filtros de comunicação mas não tem Edge Function de envio implementada. Documentado como limitação na §4.7 e como não-objetivo explícito na §5.
- **Status:** Documentado — Pergunta em aberto #10 sobre implementação futura.
